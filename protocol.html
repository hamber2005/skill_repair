必须区分的五种“再跑一次”

类型是否增加修复预算怎样记录
修改 Skill 后再执行是候选编号、修订轮次、包哈希、反馈来源
同一个包重新执行增加执行采样预算同包尝试编号，保留全部有效成功与失败
网络、限流等无效尝试重试通常增加真实成本无效原因、模型是否已产生响应、重试策略
只对保存产物重跑 verifier没有重新生成任务产物产物哈希、校验环境、原始与恢复结果

执行恢复与 Skill 内容修复需要分别报告

CausalFlow 当前 15 个最终包逐字节未变，却有 D3、Flink、制造维护 3 题通过。它们应记为未改 Skill 的重跑恢复。动作级回放成功、生成新包、最终任务通过，是三个不同事件。

SkillAxe 与 MMG2Skill 的发布评分还包含 outcome-adjusted 规则：某题执行从失败变为通过后，把诊断/修复 TP 改成该题全部 Gold 数，并把 FP、FN 置零。这个数值依赖执行结果，不能再作为独立证据证明所有 Gold 缺陷都修对。下表保留调整前的内容裁判值。

有效运行也可能含有评测环境问题

本报告的“无效执行”按上传 JSON 的 execution_ok=false 统计。execution_ok=true 且 reward=0 的记录仍可能在 verifier 内部遇到端口、依赖或网络错误。不能机械地把这一字段当作完全公平的环境证明。

下次组会需要统一的具体事项

  1. 固定同一初始失败轨迹及其完整产物；核对 original_run 内部的条件、运行 ID 和包哈希。
  2. 每个修后运行同时上传实际输入的完整 Skill 包，并让文件重算哈希与执行记录一致。
  3. 固定实际模型版本、provider、采样设置和 token/迭代上限。
  4. 固定任务镜像、verifier 和修改权限；修订矩阵等例外单列。
  5. 分别记录候选生成、修订轮次、同包复测、基础设施重试和 verifier-only 恢复。
  6. 预先规定选择最后候选、最好候选或首次通过；完整公开未选中的尝试。
  7. 同时报告任务恢复数/目标题数、有效执行数/目标题数、以及原本通过的检查项退步情况。
  8. 将内容裁判的 Gold 对齐与执行恢复分开报告；成功后自动改 TP 的分数不能当作独立语义验证。

同一“构建成功”检查，内部测试矩阵也不同

AgentOps 原始矩阵包含 Python 3.7—3.12；CausalFlow 与 MMG2Skill 的恢复记录改用 3.8—3.12。SkillRevise 的新复核中，3.10/3.11 均因 timestamp 断言失败；旧归档的 3.11 通过与 3.10 白名单错误仅保留作环境变化证据。MMG2Skill GPT 五个受测版本都通过，但该 PASS 属于修订矩阵下的 verifier-only 恢复。AgentOps构建修复 页面列出了旧矩阵与新复核的区别。
